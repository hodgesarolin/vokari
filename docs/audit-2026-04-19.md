# Vokari Full Audit — 2026-04-19

Two-model audit by Claude (Opus 4.7) and Codex (gpt-5.4), two rounds each, cross-reviewed. Full transcript + final synthesis.

---

## Executive summary

Vokari's v2 code is genuinely well-shaped: clean module boundaries, minimal dependencies (3 runtime packages), broad test coverage at the unit level, and a positioning moat nothing else in the agent-tooling space currently fills. But there are **7 specific code defects** that block a confident v1.0 launch, the **category positioning is on the wrong axis** in the README, and there's **one structural gap** — a crisp failure-mode contract — that matters more than any individual feature because the product's whole pitch is epistemic discipline.

The "Mem0 remembers what users said. Vokari tracks whether the agent's knowledge is right" line is directionally correct but benchmarks Vokari against the wrong competitive set. The actual neighbour is **Phoenix / LangSmith / Inspect AI / DeepEval** — eval and observability tools. Against that set, Vokari has a distinct offering: *live* epistemic commitments with in-process belief state, not eval runs over captured traces.

**Bottom line:** fix the 7 bugs, ship to npm, reframe the README around the eval-observability neighbourhood, add a flight-recorder demo, define the failure-mode contract, and this is a real product.

## Codex's Round 1 audit

### 1. Code quality & architecture

**Critical finding I missed:** `initDb` initializes corrections, beliefs, predictions, positions, verifications — but **NOT knowledge** (`db.ts:75`). Server/CLI remember to call `initKnowledge` manually (`server.ts:38`, `cli.ts:138`), but library consumers following the README programmatic example hit missing-table errors.

**Migration story is half-real.** `runMigration` exists (`db.ts:43`) but `initPredictions` still uses the old "try ALTER and swallow duplicate column" style (`predictions.ts:119`). `runMigration` itself is not wrapped in a transaction around SQL + migration-record — a crash between `db.exec(sql)` and `INSERT INTO _migrations` leaves ambiguous state.

**Transaction safety is mixed.** `recordVerification` is correctly transactional (`verification.ts:372`), knowledge upsert is transactional (`knowledge.ts:394`). But read-modify-write paths like `recordContradiction` (`beliefs.ts:355`) and `reviseBelief` (`beliefs.ts:435`) aren't — concurrent agents can lose appended contradictions or revision history. `createVerification` has a check-then-insert race and no partial unique index (`verification.ts:150`).

**Date-format bug risk.** JS ISO timestamps (`T`/`Z`) stored alongside SQLite `datetime('now')` output (space-separated). Lexical compares across formats can misclassify same-day due items (`predictions.ts:240`, `verification.ts:267`).

**Hard bug.** `oldest_unverified_days` uses `MIN` where "oldest" requires `MAX` (`verification.ts:590`). Dashboard displays a backwards stat.

**Test surface:** concurrency tests (`tests/concurrent.test.ts:36`) prove sequential multi-connection visibility, not true simultaneous claim contention. No MCP protocol integration test.

### 2. Feature completeness

35 MCP tools is CRUD-ish, not a day-1 integration kit. A framework author wants one object: `const vokari = await createVokari({ dbPath, namespace, clock })` plus `beforeModelCall()`, `afterModelCall()`, `recordToolResult()`, `close()`.

Missing: `retire_belief` MCP tool (function exported but not exposed); `abandon_position`; general `list_predictions`; verification history tool; bulk import/export; user/session/tenant namespace; redaction hooks; clock injection; schema-stable JSON result mode for agents that don't want markdown strings.

### 3. Market positioning

"No other tool does this" in `README.md:35` is too broad. Phoenix, LangSmith, Inspect AI already occupy "is my agent working?" through tracing + evals + datasets + observability. **Vokari's real category: local epistemic state and calibration sidecar for agents.** Wins on explicit beliefs, prediction ledgers, Brier score, MCP-native local operation, low dep burden. Loses on retrieval quality, entity graphs, embeddings, trace ingestion, hosted collaboration, eval datasets, ecosystem integrations.

Sources checked (live web): Mem0, Zep Graphiti docs, Arize Phoenix, LangChain LangSmith.

### 4. Adoption friction

Biggest blocker: packaging/docs mismatch. Package is scoped `@vokari/epistemic` (`package.json:2`) but README says `npx vokari init`. That command fails even after publish unless an unscoped `vokari` also exists. Use `npx -y @vokari/epistemic`.

No `.github`, no CI, no badges, no topics, no screenshots, no framework examples, no working Cursor config. `better-sqlite3` is a native dep — install failures are plausible and need docs. Dashboard pulls Chart.js from CDN (`dashboard.ts:178`), breaking offline/local-first claims and adding supply-chain surface.

### 5. Technical improvements

Real CI pipeline; MCP integration tests that spawn `dist/server.js` over stdio and roundtrip JSON-RPC. Timestamp normalization to ONE format (integer epoch ms OR SQLite datetime everywhere). Transaction wrappers + partial unique index for active verification claims. Numbered migration table, atomic application, tests against older fixture DBs. Benchmarks: 1K/10K/100K beliefs + knowledge + assembleContext/searchKnowledge/verificationTick latency. Property-based tests for Brier score invariants, calibration bucket boundaries, partial outcomes, confidence clamping. Prometheus/OTel metrics for belief count, unverified count, pending predictions, Brier score, verification lag, contradiction count.

### 6. Market wants

Agent builders want integrations, not primitives. LangChain/LangGraph middleware, LlamaIndex memory/context adapter, CrewAI tool bundle, AutoGen example, Vercel AI SDK, OpenAI Agents SDK, Cursor/Claude Desktop configs. Multi-agent + multi-user isolation. Cloud sync. Team dashboards. API keys. REST/HTTP mode. Hosted Vokari. Provider-agnostic verification adapters (OpenAI, Anthropic, Gemini, Ollama, LiteLLM). Phoenix/LangSmith/Inspect AI/OTel integrations → Vokari as the persistent epistemic layer BENEATH existing eval stacks.

### 7. Killer demo

*"Vokari is the black box for agent beliefs: what it thought, how confident it was, when it checked, and whether it was wrong."* Four-pane GIF: Cursor chat, MCP tool call, changed belief row, calibration dashboard. Emotional hook: catching an overconfident agent before it repeats a false claim.

### 8. Roadmap

- **v1.0:** npm publish, corrected quickstart, Cursor/Claude Desktop configs, CI, MCP integration tests, stable migrations, timestamp fix, transactional verification claims, package `exports`, Node `engines`, high-level `createVokari` API, namespace support, benchmark results.
- **v1.1:** OTel/Prometheus, Phoenix/LangSmith exports, framework adapters, optional hosted sync, REST/SSE transport, redaction policies, richer dashboard screenshots.
- **Must-nots:** not a vector DB, graph memory, autonomous truth oracle, general eval platform, or cloud-only memory product. README should explicitly say Vokari does not retrieve semantic memories like Mem0/Zep, does not prove truth, and does not replace tracing/eval.

## The one structural gap (Codex's biggest insight, Claude concurs)

**A crisp failure-mode contract.**

Vokari's product is epistemic discipline — what it *can't* compute cleanly matters as much as what it can. Today, behaviour in these scenarios is ambiguous:

- Verification is inconclusive (can't confirm or contradict)
- Migration fails partway
- Contradictory state across a retire/revise race
- Malformed MCP input
- Insufficient evidence for calibration (the 5-prediction minimum)
- Empty/null results from `getCalibration` / `getSystematicBias`
- Concurrent writers racing on check-then-insert

**Fix before v1.0:** define and document result statuses, error codes, JSON shapes for `unknown` / `insufficient-data` / `conflict` / `degraded`. Every caller needs to know when Vokari itself is uncertain vs. asserting. A tool about *knowing what you don't know* must be loud about what it doesn't know itself.

This is the single most important item of the audit that isn't a specific code line.
